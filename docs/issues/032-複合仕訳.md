## 概要

レシート 1 枚の支払いを、複数の科目に分けて登録できるようにする〔複合仕訳〕。例：スーパー 3,000 円 → 食費 2,200 円 ＋ 日用品 800 円〔日付・取引先・支払方法は同じ〕。

`transactions` の行は、今と同じ **1 行 ＝ 1 科目**のままにする。分けて登録した行を、「同じレシート」の印〔列 1 つ〕でつなぐ〔案 B〕。予実比較・自動予算・トップの集計〔`TransactionRepository` の 3 つの集計〕は変えない。

段階 2 で、まず登録画面に明細の行を足す〔保存は、印のないふつうの取引を N 件。DB は変えない〕。段階 3 で、DB に印の列を足し、編集・削除・複写をまとまり単位にする。**目標は段階 3 まで**〔段階 2 だけでは「まとめて登録」で、複合仕訳とは言えないため〕。

## 要望の内容〔2026年11月17日・本人〕

1. レシート 1 枚の支払いを、複数の科目に分けて登録したい。日付・取引先・支払方法を、行ごとに入れ直したくない。
2. 分けて登録した取引は、あとから「同じレシート」としてまとめて直す・消す・写すことができるようにしたい。
3. 他人のデータを見せない守り〔ID と `user_id` で絞る〕は、今と同じ強さに保つ。
4. JavaScript で画面を組み立てない〔要件定義書 7 章〕。JavaScript が無効でも登録できるようにする。

## 調べた結果〔2026年11月17日〕

- 「1 取引 ＝ 1 科目」を前提にしている所は、テーブル、Entity、`TransactionRepository` の 3 つの集計、取引の画面一式にある。予実比較・自動予算・トップは、すべてこの 3 つの集計を通るので、案 B なら集計は変わらない。
- テーブルを 2 つに分ける案〔案 A〕は、3 つの集計の書き直し、テストの準備〔`new Transaction(`。45 ファイル・63 か所〕の直し、今のデータの移し替えが要る。画面と流れの量は、案 A と案 B でほぼ同じ。
- アプリの DB ユーザー `hb_app` には `ALTER` の権限がない〔設計書 7.9〕。案 B の列 1 つでも、本人が `root` で `ALTER` を流す。Flyway は入れない。
- テストのときの DB の接続の数に余裕がなかったので、先に減らした〔段階 0〕。

詳しい結果、決まったことの一覧、段階、決まっていない点は、手順書にある。
