# 008：ブラウザを自動で動かすテスト（Playwright など）を入れたい

## 概要

今は、画面の確認（入力エラーの表示、ログアウト後の「戻る」、Cookie の属性、見た目など）を、**人がブラウザで行っている**（Phase 8 の 4.5〜4.10、4.16）。これを、**ブラウザを自動で動かすテスト**（Playwright など）で繰り返せるようにしたい、という要望。**Phase 8 のあとの候補**で、Phase 8 には入れない。新しい機能（アプリの動き）ではなく、**テストの道具の追加**なので、要件定義書は直さない見込み。設計書の使用技術の表（1.2）には、道具を足すことになる。

## 要望の内容

- 要望：ブラウザを自動で動かして、画面を操作し、結果を確かめるテストを入れたい。Playwright を第一候補にする。
- 理由：
  - 今の自動テストは MockMvc〔ブラウザなしで HTML の文字列を確かめる〕。**ブラウザでしか確かめられないことは、手作業のまま**残る：エラーの文字の見え方、入力欄の動き〔`type="date"`、IME の全角〕、パスワード欄が空になること、ログアウト後の「戻る」〔4.16〕、Cookie の値の変化〔ログイン前後の `JSESSIONID`。MockMvc では確かめられなかった。設計書 7.10 の C1〕。
  - 手作業は、画面を変えるたびに、同じ確認をやり直す手間がかかる。Bootstrap〔4.12〕や JavaScript〔4.16〕のような、見た目や動きの変更の確認が特に重い。
- **Phase 8 のあとの候補**にする。Phase 9 の前か後かは、あとで決める。issue 004（CSV 出力）、006（ユーザー名とパスワードの変更）と同じ扱い。

## 今の仕組み（決めるときの前提）

- 自動テストは `.\mvnw test`。1241 件〔2026年11月時点〕。**開発用の DB につなぎ**、各テストを `@Transactional` で包んで、終わると取り消す〔行は残らない〕。
- MockMvc の中で動くので、アプリは実際のポートで待ち受けていない。
- ブラウザを自動で動かすテストは、**別のスレッドでアプリに HTTP でつなぐ**ので、`@Transactional` による取り消しが**効かない**。データが DB に残る。ここが最大の違い。
- パスワードや接続先は、環境変数から読む〔`HB_DB_URL`、`HB_DB_USER`、`HB_DB_PASSWORD`〕。コード・文書・コミットメッセージには書かない〔CLAUDE.md〕。テスト用の値も同じ。
- DB のパスワードを入力する作業と、Git の操作〔コミットなど〕は、本人が行う。

## 決めること

### 1. 道具の選び方

- 候補：Playwright for Java／Selenium／Cypress など。このアプリは Java（Maven）なので、Java から書ける道具が候補になる〔Playwright for Java、Selenium〕。
- 比べる点：
  - ブラウザの種類〔Chromium、Firefox、WebKit。WebKit は iPad の Safari に近いが、**実機の iPad の代わりにはならない**〕。
  - ブラウザ本体の取得〔Playwright は初回にブラウザ本体をダウンロードする。容量と、ネットワークがない場所で動かす必要があるか〕。
  - 待ち方の安定さ〔画面が出るまで待つ処理を、自分で書かなくて済むか〕。
  - ライセンス〔多くは Apache 2.0。`THIRD-PARTY-NOTICES.md` に書くか。Bootstrap と同じ扱い〕。テストにしか使わないこと〔本番の成果物に入らない `test` の依存にする〕。
  - 書いたテストが読みやすいか〔入門者に分かる書き方。CLAUDE.md〕。

### 2. MySQL とアプリをどう動かすか

- **アプリの動かし方**：①`@SpringBootTest(webEnvironment = RANDOM_PORT)` で、テストの中でアプリを起動する。②すでに起動している開発用のアプリ〔`localhost:8080`〕にブラウザをつなぐ。
- **DB**：
  - A：今の開発用 DB〔MySQL 9.7 のサービス〕をそのまま使う。**データが残る**ので、後始末〔テスト用アカウントの削除など〕が要る。`test1`・`test2` など確認用のデータとの混ざりにも注意。
  - B：テスト専用のスキーマ〔別のデータベース名〕を同じ MySQL に作る。接続先は環境変数で切り替える。作るのは本人〔DB のパスワードを入力する作業は本人が行う〕。
  - C：Testcontainers で、使い捨ての MySQL 9.7 を起動する。きれいだが、Docker が要る。
- **テストごとの初期状態**：テストの前後でテーブルを空にするか、テストごとに新しいアカウントを作るか。
- **実行の分け方**：`.\mvnw test` は今のまま速く保ち、ブラウザのテストは別〔Maven のプロファイル、または `verify`〕にするか。ブラウザのテストは遅く、環境〔ブラウザ、DB〕に依存する。
- **秘密情報**：テスト用のユーザー名・パスワードを、コードに書かない〔環境変数、またはテストの中で毎回ランダムに作る〕。ログにも出さない〔設計書 7.9〕。

### 3. どの確認を自動にするか

- **自動にする候補**〔手作業の繰り返しが重く、ブラウザでしか確かめられないもの〕：
  - 4.7：入力エラーのメッセージの表示と、入力値が残ること、パスワード欄が空になること。
  - 4.16：ログアウト後の「戻る」でログイン画面になること〔ブラウザの bfcache の動きを自動で再現できるかも、確かめる〕。入力エラーの画面で「再送信」の確認が出ないこと。
  - 4.6：ログイン前後の `JSESSIONID` の値が変わること、`HttpOnly`・`SameSite=Lax`、URL に `;jsessionid=` が付かないこと、CSRF のトークンを消した送信が 403 になること。
  - 4.5：全画面を開いて、500 や Whitelabel が出ないこと。
  - 削除の確認ダイアログが出ること〔ダイアログを承認／キャンセルする〕。
- **自動にしない**〔人が行う〕：
  - iPad の実機の確認〔4.13、Phase 9 のリハーサル〕。ファイアウォール、ネットワークの種類。
  - 「見やすい」「読める」などの、人の目の判断。
  - MySQL のサービスを止める確認〔4.6 (7) の 7-7〕。
- 見た目の自動確認〔画像の比較〕は、フォントや絵文字の描画の違いで揺れやすいので、入れるかを別に決める〔入れない案もある〕。

### 4. README の画面の画像をこれで撮るか

- 撮る案：画面の大きさ〔ビューポート〕と見せるデータを固定でき、**誰が何度撮っても同じ画像になる**。デモ用アカウント〔Q8-14、Phase 9〕のデータを入れて、撮影用のテストで撮る。画面を変えたとき、撮り直しやすい。
- 撮らない案：自分のブラウザで手で撮る〔今の予定。Phase 9〕。道具の導入が Phase 9 に間に合わなくても、README は進められる。
- 考えること：
  - 絵文字〔issue 005 の 💮〕やフォントの描画が、撮る環境で正しく出るか。
  - パスワードや接続情報が画像に写らないこと〔設計書 7.9〕。アドレス欄、開発者ツールを写さない。
  - iPad の縦・横の画像を、WebKit の端末の設定〔iPad の画面サイズ〕で近い画像にできるか。実機の画面そのものではない点を、README に書くか。
- Phase 9 の画像は、この issue より先に、手で撮ることになる可能性が高い。その場合、あとで撮り直すか。

### 6. JavaScript を使う機能との関係（2026年11月4日。本人の判断。[issue 009](009-金額を入れやすくするボタン.md) から）

**JavaScript を使う決まりは、本人の判断でゆるめてよいことにした**〔よい機能は入れていきたい〕。ただし、決まりを変えるのは、**JavaScript を使う機能を実際に作るときに、要件定義書・設計書から行う**〔いま文書は変えない〕。そのとき、**ブラウザで動きを確かめる方法も一緒に決める**。

- 今の自動テスト〔MockMvc〕は、**JavaScript の動きを確かめられない**〔ボタンを押して欄の値が変わる、など〕。JavaScript を使う機能が増えるほど、この issue のブラウザを自動で動かすテストの必要が高くなる。
- 決めること：JavaScript を使う機能を作る**前に**、この issue の自動テストを入れるか。機能と一緒に入れるか。人がブラウザで確かめるだけにするか。
- 「Bootstrap の JavaScript は入れない」は別の決まりで、この判断では変えない。

### 7. issue 009 の金額ボタンを、自動で確かめる（2026年11月5日。Codex のレビューの指摘。[issue 009](009-金額を入れやすくするボタン.md) から）

- **issue 009 の金額ボタン：端数・境界値・税込のロックと解除を自動で確かめる。**
- きっかけ：issue 009 の Codex のレビューで、「今のテストは、ソースと HTML を確かめていて、計算やクリックの動きを実行していない。`Math.floor` を `Math.ceil` に変えても気づけない」と指摘された。
- 今は、計算は Console の 32 件、動きは 4.7 の手順を、**人がブラウザで**確かめた。自動テストは、HTML に印があること、JavaScript のソースに禁止の書き方がないこと、までしか確かめていない。
- 自動で確かめたいこと：端数の切り捨て〔税込（10%）・税込（8%）〕、境界値〔909091・909092、999999 に +1、先頭のゼロ、10 桁〕、税込のロックと解除〔押したあと、足すボタンでは解除されない。手で書き換える・空にする・クリアで解除される。金額が入った状態で開いた画面は、最初からロック〕、クリアで欄が空になり、カーソルが戻ること。
- 決めること：この issue の道具〔Playwright など〕で行うか、計算の 2 つの関数だけを JavaScript の単体テストで確かめるか〔新しい道具の話になるので、「JavaScript の決まり」と合わせて決める〕。
