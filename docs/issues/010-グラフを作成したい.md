## 概要

ログインしたあとに開く**「トップ」画面**を新しく作る。今の季節と今週の使い方が、**メーターと円グラフで一目で分かる**ようにする。メニューの先頭に「トップ」を足し、ログインしたあとは、取引一覧ではなくトップに移る。

JavaScript もライブラリも使わない。円グラフもメーターも、**HTML と CSS だけ**で描く〔円グラフは CSS の `conic-gradient`〕。

**要件定義書にない機能**なので、行うときに、要件定義書に加える〔直す前と後の文を先に見せる。手順書の付録 A〕。**週の予算・100 円単位の切り上げは、新しい決まり**で、要件定義書に入る。

## 要望の内容

- 理由：表の数字を読むより、「予算に対してどれだけ使ったか」「日の進み方と比べて早いか遅いか」「今週何に使ったか」が、一目で分かるため。

## 決まったこと（2026年11月8日。本人。デザインの案で決めた）

### 画面の全体

- 新しい「**トップ**」画面を作る。**メニューの先頭**に「トップ」を足す。**ログインしたあとはトップに移る**〔今は取引一覧〕。
- 画面の**右上**に、「**予実比較を見る**」と「**取引を登録**」を置く。
- 上から順に、次の 3 つ。

### 1. 季節のメーター

- **今の季節の合計だけ**〔科目ごとには出さない〕。
- 「**使った額 / 予算**」と「**残り**」を、**1 円単位**で出す。
- 棒は、**予算に対して使った割合**。縦の線は「**今日**」〔季節の何 % まで日が進んだか〕。

### 2. 今週の円グラフ

- 今週、何に使ったか。**使っていない科目は出さない**。
- 真ん中に**今週の合計**。横に、**科目・金額・割合**の一覧。
- 色は**ターコイズの濃淡と灰色だけ**〔赤・青・💮 の色は使わない〕。
- **CSS の `conic-gradient` で描く**。JavaScript もライブラリも使わない。

### 3. 今週の科目ごとのメーター

- 科目ごとに、「**今週の実績 / 週の予算**」の棒と、縦の線「**今日**」〔週の何日目か〕。
- いちばん上に**合計の行**。

### 計算の決まり

| 項目 | 決まり |
|---|---|
| 今週 | **日曜〜土曜**。季節をまたぐ週は、前の季節の取引もそのまま入れる |
| 週の予算 | **「今日が入っている季節」の科目の予算 ÷ 13** を、**100 円単位で切り上げ** |
| 今週の実績 | **100 円単位で切り上げ**〔円グラフもメーターも〕。円グラフの割合も、切り上げた額から出す |
| 合計 | 予算も実績も、**科目ごとに切り上げた額を足したもの** |
| 今週の色 | 予実比較と同じ決まり〔**赤：超過、青：1/3 以下、💮：1/3 を超えて予算以下、予算 0 円なら色なし**〕を、**週の予算**に当てはめる。判定は、**画面に出ている切り上げ後の額**で行う |
| 画面の言葉 | 予実比較と混ざらないよう、「**今週の**」「**週の予算**」と書く |
| 見た目 | [issue 015](015-見た目をそろえる.md) の決まり〔色・フォント・角の丸み〕に合わせる。💮 の行の背景は `#FFF2E5` |

### 決めること（例）

- **何をグラフにするか**：
  - 予算と実績の比較〔科目ごとに、予算と実績を並べる。今の予実比較の表に近い〕。
  - 季節ごとの実績の移り変わり〔春・夏・秋・冬、年をまたぐ変化〕。
  - そのほか〔科目ごとの割合、など〕。
  - 今の画面〔予実比較の表〕で足りない点が、何かを先に確かめる。
- **どの画面に置くか**：予実比較の画面の中、または新しい画面〔例：`/graphs`〕。メニューの項目〔今は 7 つ〕が増えるか。
- **グラフを描く方法**：
  - JavaScript のライブラリを使う〔ブラウザで描く。見た目の自由度が高く、動きも付けられる〕。ライブラリのライセンスの表示〔`THIRD-PARTY-NOTICES.md`〕と、アプリの中に 1 ファイルで置くこと〔CDN を使わない。会場でインターネットにつながらなくても動く。設計書 1.2〕を考える。
  - サーバー側で作る〔画像や SVG を HTML として返す。JavaScript は要らないが、描く部品を自作することになる〕。
  - CSS だけで作る簡単な棒グラフ〔Bootstrap の進行バーなど。種類は限られる〕。
  - **JavaScript の決まりとの関係は、[issue 008](008-ブラウザを自動で動かすテスト.md)・[issue 009](009-金額を入れやすくするボタン.md) と同じ**：JavaScript を使う決まりは、本人の判断でゆるめてよい。ただし、決まりを変えるのは、JavaScript を使う機能を実際に作るときに、要件定義書・設計書から行う。そのとき、ブラウザで動きを確かめる方法〔issue 008 の自動テストを先に入れるか、など〕も一緒に決める。「Bootstrap の JavaScript は入れない」は別の決まりで、変えない。
- **色の決まりとの関係**：予実比較の色〔赤＝予算を超えた、青＝予算の 1/3 以内、💮・薄い緑＝予算の 1/3 を超えて予算内、色なし＝予算 0 円・実績 0 円〕を、グラフにも使うか。同じ意味の色を使うと分かりやすいが、グラフの棒を赤・青で塗ると、「超えた・余裕がある」の判定をグラフでも行うことになる〔判定を 1 か所に置く決まり。`BudgetColorJudge`〕。色だけに頼らず、数字や文字も添える〔色の見分けにくい人にも伝わる〕。
- **自動テストで確かめられること・できないこと**：グラフに渡すデータの正しさ〔集計〕は、今の自動テストで確かめられる。描かれた見た目や動きは、MockMvc では確かめられない。人がブラウザで確かめるか、issue 008 で確かめる。
- **データの分離**：グラフに使うデータも、ID と `user_id` の両方で絞る〔CLAUDE.md、設計書 3.9〕。他の人のデータを集計に混ぜない。
- **狭い画面での表示**：iPad の縦・横で、グラフが収まるか。
- **変える文書**〔行うと決めたとき〕：要件定義書 → 設計書 → 手順書、の順。
