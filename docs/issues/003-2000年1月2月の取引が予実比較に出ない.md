# 003：2000年1月・2月の取引が、予実比較に表示されない

## 概要

取引の日付は 2000年1月1日から入力できるが、2000年1月・2月は「1999年の冬」に入る（冬は12月がある年、設計書 5.8）。予実比較で表示できる季節は 2000年春から（設計書 2.4）なので、**2000年1月・2月の取引は、どの季節の画面にも出ない**。Phase 7 の 4.4（`ComparisonService` の作成）で分かった。動きは設計書 2.4 に書いてあるとおりで、仕様どおりの端の挙動だが、集計されない取引を入力できてしまうのは不自然なので直す。

## 要望の内容

- 現状：
  - 取引の日付の範囲は 2000-01-01〜2100-12-31（要件定義書 5章、設計書 2.3、3.6、6.6、DB の CHECK 制約 `ck_transactions_date`、`TransactionDateRange`）。
  - 予実比較・予算設定の季節の範囲は、2000年春〜2100年冬（設計書 2.4、`SeasonPeriod.isInRange`）。
  - そのため、2000-01-01〜2000-02-29 の取引は、取引一覧には出るが、予実比較では集計されない。
  - 上限側は合っている。2100年12月は 2100年冬に入り、日付の上限 2100-12-31 は取りこぼさない。
- 自動テストでは、この動きを確かめてある（`TransactionRepositorySumTest.transactionsOfJanuaryAndFebruary2000AreNotInAnyDisplayedSeason`、`ComparisonServiceTest.transactionsOfJanuaryAndFebruary2000AreInNoDisplayedSeason`）。

## 決めたこと

- **取引の日付の下限を 2000-03-01 にする。上限 2100-12-31 は変えない。** 理由：季節の範囲（2000年春〜2100年冬）と、取引の日付の範囲をそろえるため。これで、入力できる取引は、すべて予実比較のどこかの季節に入る。
- 採らなかった案：
  - 季節の範囲を 1999年冬からにする：予算の `season_year` の CHECK 制約（2000〜2100）、`SeasonPeriod` の範囲、予算設定の範囲、各画面のテストまで広がるため。
  - 直さない：集計されない取引を入力できてしまうため。
- 直す場所（Phase 7 の途中で入った直しとして、`phase-7-comparison.md` に記録する）：
  1. 要件定義書 5章の文（直す前と直した後の文を見せて、確認してから直す）
  2. 設計書：2.3（取引登録の日付の制限）、2.4（2000年1月・2月の取引の説明）、3.6（`transactions` の `transaction_date`）、6.6（日付の範囲）、R12 に関わる記述
  3. 手順書：`phase-7-comparison.md`
  4. コード：`TransactionDateRange`、エラーメッセージ（`messages.properties`）、`schema.sql` の CHECK 制約があればそれも、テスト（境目：2000-02-29 はエラー、2000-03-01 は OK）
- 開発用の DB の既存の取引に、2000-03-01 より前の日付のものはない（確認は直す前に行う）。`schema.sql` は `CREATE TABLE IF NOT EXISTS` で既存のテーブルを変えないため、CHECK 制約を変えるときは、既存の DB の制約を直す手順が要る（あなたが `root` で実行する SQL を示す）。

## 対応状況

対応済み（要件定義書・設計書・手順書・コード・テストを直し、開発用 DB の CHECK 制約を付け替えた。`.\mvnw test` は 1184 件すべて成功）
