# 009：金額の入力を楽にしたい（+1・+10・+100・+1000 のボタンの案）

## 概要

取引の金額と予算の金額を入力するのを、今より楽にしたい、という要望。案として、金額の欄の近くに **+1・+10・+100・+1000 のボタン**を置く。**今は記録だけ**で、コードも設計書も変えない。**行うかどうかは、4.9 のリハーサルで、iPad で金額を打ってみてから決める。**

## 要望の内容

- 要望：金額の入力を楽にしたい。案は、+1・+10・+100・+1000 のボタン。押すたびに、欄の数に足される。
- 理由：iPad やスマホでは、数字を打つのが手間に感じることがある。

## 今の状態（調べた結果。2026年11月4日。読むだけで調べた。コードは変えていない）

金額を入力する欄は、**2 か所**。**どちらにも `inputmode="numeric"` の指定がある**。

| 画面 | ファイル | 欄 |
|---|---|---|
| 取引の登録・編集 | `templates/transactions/form.html`（32 行目） | `<input class="form-control" type="text" inputmode="numeric" th:field="*{amount}">` |
| 予算設定 | `templates/budgets/form.html`（44 行目） | `<input class="form-control" type="text" inputmode="numeric" th:field="*{rows[__${stat.index}__].amount}">` |

- `type` は `text`〔`number` ではない〕。全角の数字を受け付けるため〔要件 5 章、Phase 8 の R13〕。
- `inputmode="numeric"` は、iPad・スマホで**数字のキーボードを出す指定**。Phase 8 の 4.13 の確認項目に「金額の欄で数字のキーボードが出る」があり、iPad の Safari で、期待どおりだった〔Phase 8 の手順書 4.13 の記録〕。
- 金額の欄を持つほかの画面はない。科目・取引先・支払方法・摘要の欄は文字の入力で、`inputmode` は付けていない〔付けなくてよい〕。
- **今の JavaScript は 2 つだけ**：削除の確認ダイアログ〔フォームの `onsubmit`〕と、`static/js/back-reload.js`〔ブラウザの「戻る」の対策〕。

## 決めること

- **本当に楽になるか**：
  - 予算のような**切りのよい金額**〔30,000 円、25,000 円など〕では、+1000 を押す回数が多いが、数字を打つよりは楽かもしれない。
  - **細かい金額**〔1,234 円など〕は、+1・+10・+100・+1000 を何度も押すことになり、**打つより遅くなる**。
  - 押すより打つ方が速い場面が多い可能性がある。**（2026年11月5日）iPad での確認は行わないことにした。実装して、PC のブラウザで、手で打つ場合とボタンの場合を比べて判断する。**
- **`inputmode` で足りるか**：すでに数字のキーボードは出る。それで足りて、ボタンは要らない、となる可能性がある。実装して、PC のブラウザで比べる。
- **ほかの案**：ボタンの代わりに、「よく使う金額」の候補、前回と同じ金額の複写、など。要望の本当の困りごと〔何が手間か〕を、PC のブラウザで確かめてから比べる。
- **JavaScript が要る**：ボタンで欄の値を変えるには、ブラウザ側の処理〔JavaScript〕が要る。今の決まりでは、JavaScript は少量〔削除の確認、「戻る」の対策〕だけで、画面を JavaScript で組み立てない〔設計書 1.1〕。→ 下の「JavaScript の決まりについて」。
- **自動テストで確かめられないこと**：今の自動テスト〔MockMvc〕は、HTML の文字列を確かめるだけで、**ボタンを押したときの動きは確かめられない**。ボタンが HTML にあること、`inputmode` があることは確かめられる。動きは、人がブラウザで確かめるか、issue 008〔ブラウザを自動で動かすテスト〕で確かめる。
- **入力チェックとの関係**：ボタンで足した値も、今までどおり、サーバー側で入力チェックされる〔1〜1000000 の整数、要件 5 章〕。上限を超えたとき、ボタンを無効にするか、そのまま送ってエラーにするか。空欄のとき、`+` が何を足すか〔0 から〕。全角の数字が入っているときの扱い。
- **狭い画面での置き場所**：
  - 取引の登録：金額の欄の下に 4 つのボタン。iPad の縦・横、スマホの幅で折り返しても押せるか。
  - **予算設定**：科目の行ごとに欄がある〔最大 256 行〕。行ごとにボタンを 4 つ置くと、表が広がる。置かない〔取引だけにする〕案もある。
  - 親指で押せる大きさと間隔。
- **変える文書**〔行うと決めたとき〕：要件定義書〔画面の部品の追加。直すかは、その時に決める。直すときは、直す前と後の文を先に見せる〕、設計書〔2.3 の画面の部品、JavaScript の使い方〕→ 手順書、の順。

## JavaScript の決まりについて（2026年11月4日。本人の判断）

**JavaScript を使う決まりは、本人の判断でゆるめてよいことにした**〔よい機能は入れていきたい〕。ただし、**決まりを変えるのは、JavaScript を使う機能を実際に作るときに、要件定義書・設計書から行う**〔いま文書は変えない〕。そのときは、**ブラウザで動きを確かめる方法も一緒に決める**〔[issue 008](008-ブラウザを自動で動かすテスト.md) の自動テストを先に入れるか、人がブラウザで確かめるか、など〕。

- ゆるめるのは、**自作の短い JavaScript** についての決まり〔設計書 1.1〕。**「Bootstrap の JavaScript は入れない」は、別の決まりで、この判断では変えない**〔要件定義書 7 章、設計書 1.2〕。
- 変えないもの：利用者の入力を JavaScript の中に埋め込まない〔設計書 7.5〕。画面を JavaScript で組み立てない〔設計書 1.1〕。CSRF 対策を無効にしない〔CLAUDE.md〕。`th:utext` を使わない〔CLAUDE.md〕。
