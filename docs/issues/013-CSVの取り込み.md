# 013：CSV ファイルを取り込んで、取引をまとめて登録したい

## 概要

CSV ファイルを取り込んで、取引をまとめて登録できるようにしたい、という要望。**実装は予定している**が、**今は記録だけ**で、コードも要件定義書も設計書も変えない。**[issue 004](004-CSV出力.md)（CSV 出力）のあとに行う**〔まず出力の形を決め、その形を取り込めるようにするため〕。**要件定義書にない機能**なので、行うと決めたときに、要件定義書に加えるかを決める〔直す前と後の文を先に見せる〕。

## 要望の内容

- 要望：CSV ファイルを取り込んで、取引をまとめて登録したい。
- 理由：1 件ずつ画面から入れる手間を減らしたい。Excel などで作った表や、ほかから集めた明細をまとめて入れたい。

## 今の状態（調べた結果。2026年11月4日。読むだけ）

- ファイルを受け取る画面・処理は、**まだない**〔今は、フォームの文字の入力だけ〕。
- アップロードできるファイルの大きさについて、`application.properties` に**指定はない**〔Spring Boot の標準値が使われる。標準値は、実装のときに確かめる〕。
- 取引の入力チェックは、画面からの登録〔`TransactionForm`〕の決まり：日付は 2000年3月1日〜2100年12月31日、金額は 1〜1000000 の整数〔全角の数字も受け付ける〕、摘要は任意、科目・取引先・支払方法は、**このユーザーのもの**から選ぶ。
- 科目・取引先・支払方法は、**1 人あたり 256 個まで**〔要件定義書 5 章〕。名前は、同じユーザーの中で重複不可〔大文字・小文字を区別しない〕。

## 決めること（例）

- **どんな CSV を受け入れるか**：
  - A：このアプリが出力した形〔issue 004 で決める形〕。
  - B：カード会社や銀行の明細〔会社ごとに列も文字コードも違う〕。
  - **まずは A を想定**する。B は、会社ごとの対応が要るので、別の要望にする案。
- **1 行ずつの入力チェック**：**画面からの登録と同じ決まり**にする〔入力チェックを 1 か所にそろえ、`TransactionForm` の決まりを使い回せるか。金額の全角の数字、日付の形〔`2026-11-02` など〕、摘要の長さ〕。取り込み用に決まりを増やさない。
- **科目・取引先・支払方法を、名前で探す**：
  - **見つからないとき**：エラーにするか、新しく作るか。
  - 作る場合：**1 人 256 個の上限**を超えないこと。名前の長さの決まり〔取引先名は 20 文字以下など〕。大文字・小文字だけが違う名前は同じものとして探す。作るのは、確認のあと〔保存のとき〕だけ。
  - 探すときは、**このユーザーの科目・取引先・支払方法**だけから探す〔ID や名前で探すときも、`user_id` で絞る。CLAUDE.md、設計書 3.9〕。
- **エラーの行があったとき**：
  - 全部取り込まない〔1 行でもおかしければ、1 件も保存しない〕。
  - 正しい行だけ取り込む。
  - どちらにしても、**どの行が、何でおかしいか**を画面に出す〔行の番号と、理由の文〕。全部取り込まない案は、1 回のトランザクションで保存し、途中で失敗したら全部取り消す〔Phase 3 の登録と同じ考え方〕。
- **取り込む前に、一覧で確認してから保存するか**：ファイルを送る → 取り込み内容の一覧〔エラーの行も〕を見る → 「保存」を押して初めて保存、の 2 段階にするか。2 段階にすると、**確認する間、取り込んだ内容を、どこに持つか**〔セッション、または保存せずに再送信〕を決める必要がある。
- **同じファイルを 2 回取り込んだときの扱い**：そのまま 2 倍に増える／同じ内容の取引〔日付・金額・科目・取引先・支払方法・摘要が同じ〕を、重複として知らせる・飛ばす。**取引には、重複を見分ける ID がない**ので、完全に一致するかで見分けることになる〔同じ日に同じ買い物を 2 回した取引と区別できない〕。
- **文字コード**：Excel で保存した CSV は、UTF-8〔BOM 付き〕でなく、Shift_JIS〔Windows の標準〕のことがある。UTF-8〔BOM の有無〕だけ受け入れるか、Shift_JIS も受け入れるか〔自動で見分けるか、選ばせるか〕。issue 004 の出力の文字コードと合わせる。文字化けしたときの表示。
- **ファイルの大きさと行数の上限**：アップロードの大きさの上限と、取り込む行数の上限〔メモリに全部ためない、時間がかからない〕。上限を超えたときの文。
- **CSRF 対策**：ファイルを送るフォームにも、CSRF のトークンを付ける〔無効にしない。CLAUDE.md〕。ファイルを送る形式〔`multipart/form-data`〕でも、トークンが送られ、確認されること。
- **ログイン中のユーザーのものとして保存すること**：保存する取引の `user_id` は、ログイン中のユーザーにする。CSV の中に、ユーザーを指定する列があっても、使わない〔他人の ID を指定して取り込めてはならない〕。
- **ファイルの扱い**：送られたファイルは、ディスクに保存せずに、その場で読む〔保存するなら、置き場所と削除〕。ファイルの種類の確認〔拡張子、中身〕。CSV の読み取りを、自作にするか、ライブラリを使うか〔引用符、カンマ・改行を含む値の扱い。ライブラリを使うなら、ライセンスの表示〕。
- **CSV インジェクション**：取り込んだ値を、画面に出すときは `th:text`〔XSS 対策。`th:utext` は使わない〕。取り込んだ値が、あとで CSV に出力されるとき〔issue 004〕の数式インジェクションの対策は、004 の決まりに従う。
- **自動テスト**：1 行ずつの入力チェック、探し方〔見つからない・256 個の上限〕、全部取り込まない場合に 1 件も保存されないこと、**他のユーザーの科目・取引先を使えないこと**〔2 人のユーザーで〕、未ログインのとき、CSRF のトークンがないときの 403、大きさの上限、文字コード。
- **どの画面に置くか**：取引一覧のボタン、または専用の画面〔例：`/transactions/import`〕。
- **変える文書**〔行うと決めたとき〕：要件定義書 → 設計書 → 手順書、の順。
- **作ったら、PR の前に Codex にも見てもらう**〔ファイルを受け取る機能は、入力が大きく、セキュリティに関わるため。Phase 9 の 4.7 のように、指摘は、まず確かめてから、直すかを決める〕。
