# Phase 1：設計の確定

全体の位置づけは [実行計画書](execution-plan.md) を見てください。この文書は Phase 1 を実際に進めるための手順書です。

- 前の Phase：[Phase 0 開発環境の準備](phase-0-environment.md)（☑ 完了）
- 次の Phase：[Phase 2 プロジェクトの土台づくり](execution-plan.md#phase-2プロジェクトの土台づくり)
- 状態：◐ 要件定義書の修正まで完了。設計書の作成中

## 1. 目的

作る前に「何をどう作るか」を決めて、手戻りを減らします。成果物は設計書 `docs/reviews/design.md` です。

- 設計書は、**要件定義書に書いてあることだけ**を形にします。要件にない機能は足しません。
- 要件定義書で決まっていないことは、**勝手に決めず**、「5. 決まっていない点」に一覧にして確認します。確認できてから設計書に書きます。

## 2. 前提と、この Phase でやらないこと

- 入力にするのは [要件定義書](../reviews/requirements.md) と [実行計画書](execution-plan.md)。
- やらないこと：コードを書く、Spring Boot プロジェクトを作る、MySQL にテーブルを作る（すべて Phase 2 以降）。
- 設計書は日本語で、入門者が読めるように書く。コードは書かない（表・図・文章だけ）。
- 要件にない決定には「（提案）」、技術の選定には理由を1行つける。
- 要件定義書は、**直す箇所の一覧（直す前の文と直した後の文）を見せて承認をもらってから**直す。

#### 照合順序の検討項目（Q9・Q10 の補足。設計書の章3に書く）

MySQL 標準の照合順序（`utf8mb4_0900_ai_ci`）は、「大文字・小文字」「濁点の有無（例：カ と ガ）」「ひらがなとカタカナ」「全角と半角」を同じとみなす可能性があります。日本語の科目名などで、重複チェックが誤動作する（別の名前なのに「すでにあります」となる）おそれがあります。

- 設計書の章3に「照合順序をどうするか」を**検討項目として書く**（候補：標準のまま / 文字を区別する照合順序にする / 重複チェックをアプリ側で行う）。
- **Phase 2 で、実際に MySQL で試して決める**（例：`カ` と `ガ`、`ひ` と `ヒ`、`ｱ` と `ア`、`A` と `a` を登録して重複扱いになるかを確認する）。
- ユーザー名は Q20 で半角英数字のみになるため、確認の中心は科目・取引先・支払方法の名前（日本語）と、ユーザー名の大文字・小文字。

## 9. 後続 Phase への影響

決定によって、実行計画書の仮タスクが変わる箇所です。Phase 1 の最後（4.7）に反映します。

| 2 | `schema.sql` は `CREATE TABLE IF NOT EXISTS`、`DROP TABLE` なし。ベースパッケージは `io.github.yutaro081.householdbudget`。**照合順序を実際に試して決める**。Spring Boot は 4.1.1 を使う |
