## 1. 目的

このアプリの中心機能である、取引の一覧・登録・詳細・編集・削除を作ります。次の5つがそろった状態にします。

- 5つの操作が、設計書 2.2 の URL と画面のとおりに動く。入力エラーのときは、入力値が残る（設計書 2.3、6.9）。
- Phase 4 の型（「ID と `user_id` の両方で絞る」、変更の POST は先に ID を確かめる）を、そのまま取引に使う。登録・更新で選んだ科目・取引先・支払方法が**自分のものか**も確かめる（設計書 3.9、6.7）。
- 金額・日付・摘要の入力チェックが、境界値で正しく動く。DB の CHECK 制約が最後の守りとして働くことも確かめる（設計書 6.2、6.5、6.6）。
- 一覧・詳細で、科目・取引先・支払方法をまとめて読み込む（設計書 4.6）。D5（`open-in-view`）と D6（摘要の空白と NULL）を決めて、設計書に書く（設計書 8.2）。
- 取引で使用中の科目・取引先・支払方法が削除できないことを、取引の画面から確かめ直す（Phase 4 の Q4-2 の C）。

### 3.1 「ID と `user_id` の両方で絞る」型を、取引に当てはめる

| 層 | 決まり（Phase 4 の 3.1 と同じ） |
|---|---|

### 3.2 Service がやること

| 操作 | 中身 |
|---|---|
| 一覧 | 上の一覧の検索を呼ぶ |
| 1件取得 | `findByIdAndUserId`。なければ `NotFoundException` |
| 登録 | ① 科目・取引先・支払方法を、`CategoryService.get(userId, id)`、`VendorService.get(...)`、`PaymentMethodService.get(...)` で取り出す（他人・存在しないなら `NotFoundException`、何も保存しない）。② `Transaction` を作って保存（`user_id` はログイン中のユーザー） |
| 更新 | ① 取引を ID と `userId` で探す。② 科目・取引先・支払方法を、登録と同じ方法で取り出す。③ 値を入れ替える（`user_id` は変えない） |

- 更新するメソッドは、1つのトランザクションにする（5.1）。
- プルダウンの選択肢は、Controller が各 Service の `list(userId)` を呼んで、自分のものだけを登録順に並べる（6.7）。

#### 型変換の実験（Q5-1）の結果と決定

Spring 標準の変換（`Integer` の項目）を、MVC が使うのと同じ変換サービスで試した（使い捨てのテスト。削除済み）。結果は設計書 6.5 に書いた。

| 入力 | 標準の変換の結果 | 6.5 の期待との違い |
|---|---|---|
| 空、半角の空白だけ、全角の空白だけ | `null`（必須エラー） | なし（予想は外れ、期待どおり） |
| `123`、` 123 ` | 123 | なし |
| `１２３`（全角数字） | 123 として通った | **あり** |
| `1 000`（途中に空白） | 1000 として通った | **あり** |
| `0x10`、`#10` | 16 として通った | **あり** |
| `+5` | 5 として通った | **あり**（決定により、型変換のエラーにする） |
| `1,000`、`1.5`、`10円`、`99999999999`、`1e3` | 型変換のエラー | なし |
| `-5`、`010` | -5、10 | なし |

**決定（Q5-1 の C）**：専用の厳しい変換（`StrictIntegerEditor`）にする。規則は、前後の空白を `strip()` で取り除き、空なら `null`（必須エラー）。半角の数字だけ、または先頭の `-` と半角の数字だけを整数として読む。それ以外（全角数字、途中の空白、`0x10`・`#10`、カンマ、小数、`10円`、`+5`）と、範囲外の大きな数は、型変換のエラー。

- [x] 上の入力を試し、結果を表にして、設計書 6.5 に書いた
- [x] 決定に従って `StrictIntegerEditor` を作り、**食い違いがなくなるテストを残した**（`StrictIntegerEditorTest`：実験で試した入力のすべて。`TransactionFormTest`：束縛したときの型変換・必須・範囲のエラー）

## 7. つまずいたとき

| 症状 | 考えられる原因 | 対処 |
|---|---|---|
| 他のユーザーの取引が、一覧に出る | 一覧の検索が `user_id` で絞られていない | Repository の一覧が `userId` を引数に取っているか、Service が `userId` を渡しているか確認する |
| 他人のIDの詳細・編集が、404 でなく開ける | 「ID だけ」で探している | `findById` を使っていないか確認する。`findByIdAndUserId` にする（3.1） |

| 一覧が遅い／SQL がたくさん出る | 取引1件ごとに、科目などを別々に読んでいる（N+1） | 一覧の検索が、関連をまとめて読み込んでいるか確認する。4.3 のテストで SQL の数を確かめる |

## 8. 次の Phase への引き継ぎ

- Phase 6（予算）：金額の型変換の結果（Q5-1）を、予算額の入力にも当てはめる（B5）。`BudgetForm` の予算額は、同じ変換を使う。整形（`30,000円`）の方法（Q5-9）も、予算設定の画面に使える。
- Phase 7（予実比較）：`TransactionRepository` に、期間内の科目ごとの合計（`CategoryActual`、設計書 4.6）を足す。日付の範囲が 2000-01-01〜2100-12-31 に収まる（R12）ことが、季節の範囲（2000年春〜2100年冬）の前提になる。金額の整形は、差額のマイナス（`-5,000円`）にも使う。
- Phase 8（仕上げ）：取引の画面を、2人のユーザーでの確認（一覧、詳細、編集、削除、登録の科目などのID）に含める。D5 の結果で、エラー画面（5xx）の確認に影響がないかを見る。「ID と `user_id` の両方で絞る」型が取引でも守られているかを、コードを検索して確かめる。
- 設計書の章8に残る未決事項は、Phase 5 の終了時点でなくなる（D5・D6 が決まるため）。
