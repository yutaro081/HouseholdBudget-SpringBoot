## 1. 目的

「ユーザーごとのデータ分離」の土台になる認証を完成させます。具体的には、次の5つがそろった状態にします。

- アカウントを登録できる。登録と同時に、初期データ（科目3・今の季節の予算3・取引先3・支払方法2）が、そのユーザー専用に作られる（設計書 3.11、5.3）。
- ログイン・ログアウトできる。ログインしていない人は、ログイン画面・登録画面以外を開けない（要件6章、設計書 7.3）。
- ログイン中のユーザーのIDを、Controller が取り出せる（`LoginUser`、3.9。以降の Phase のすべてが使う）。
- 共通の画面の枠、404 / 403 / 500 の画面、セッション Cookie の設定（S1）ができている。
- Phase 2 の仮のページが、本物に置き換わっている。

## 2. 前提と、この Phase でやらないこと

- Phase 2 が完了し、`main` に取り込み済み（タグ `phase-2-done`）。環境変数 `HB_DB_URL`、`HB_DB_USER`、`HB_DB_PASSWORD` が設定された VS Code で作業する。`root` はアプリで使わない（実行計画書 ルール8）。

- 既定のアカウントや、決まったパスワードは作らない（S6）。動作確認用のアカウントは、自分で登録する。
- **この手順書にも、コードにも、設定ファイルにも、確認用アカウントのパスワードを書かない。**

### 4.5 D4：エラーの重なりをどう扱うかを決める（設計書 8.2）

Bean Validation は、注釈のチェックの順番を保証しない（G7）。そのため、1つの項目に複数のエラーが重なることがある。**最初の Form である `RegisterForm` で、方法を試して決めた。** 以降の Phase 4〜6 は同じ方法を使う。

- [x] 優先順を確認する：「必須 → 型変換 → 形式 → 文字数・範囲」（6.9）。`RegisterForm` で効くのは「必須 → 形式 → 文字数」
- [x] 重なるエラーを再現する（ユーザー名が空、パスワード `あ` など）
- [x] 方法を試す。実験は、実際の画面と同じ仕組み（`DataBinder`、Spring Boot の Validator、`messages.properties`）で行った。実験用のテスト（`D4ExperimentTest`）は、結果をこの手順書に残したので消した（コミットしない）

試した方法：

| 候補 | 内容 |
|---|---|
| A | 素直に、必須・形式・文字数の注釈を並べる |
| B | A に加えて、形式の正規表現が空文字を通すようにして、重なりを減らす |
| C | グループで順番を付ける（必須 → 形式 → 文字数。前のグループにエラーがあれば、後ろは調べない） |
| D | 項目ごとに自作の注釈を1つ付け、優先順に調べて1つだけエラーにする |

#### 実験の結果（1つの項目に出たエラーの数）

ユーザー名は、前後の空白（全角を含む）を `strip()` で取り除いてから検査した。もう一方の項目は正しい値にした。

| 入力 | A | B | C | D |
|---|---|---|---|---|
| ユーザー名が空 | 2 | 1 | 1 | 1 |
| ユーザー名が半角の空白だけ | 2 | 1 | 1 | 1 |
| ユーザー名が全角の空白だけ | 2 | 1 | 1 | 1 |
| ユーザー名 `あいう` | 1 | 1 | 1 | 1 |
| ユーザー名 `abcdefghijk`（11文字） | 1 | 1 | 1 | 1 |
| ユーザー名 `あいうえおかきくけこさ`（全角11文字） | 2 | **2** | 1 | 1 |
| ユーザー名 `abc def`、`ａｂｃ`（全角英数） | 1 | 1 | 1 | 1 |
| ユーザー名 ` abc `、全角の空白つき `abc`、`abcdefghij`、`abc` | 0 | 0 | 0 | 0 |
| パスワードが空 | 3 | **2** | 1 | 1 |
| パスワードが半角の空白3つ | 2 | **2** | 1 | 1 |
| パスワード `あ` | 2 | **2** | 1 | 1 |
| パスワード `abc12`、`abc1234`（7文字）、31文字 | 1 | 1 | 1 | 1 |
| パスワード `あいうえおかきく`、`abc 1234`、`abcd1234 `（末尾に空白） | 1 | 1 | 1 | 1 |
| パスワード `abcd1234`、30文字、`Pass!@#$` | 0 | 0 | 0 | 0 |

#### 優先順の確認

- C と D は、エラーが重なる入力でも、必ず優先順の高い1つが出た。
- A と B は、重なったときの**表示の順番が一定ではない**。同じ入力でも、`[形式, 必須]` と `[必須, 形式]` のように順番が入れ替わった。
- B で残る重なりは、次の3つ。いずれも「形式」と「文字数」、またはパスワードが空のときの「必須」と「文字数」。
  - ユーザー名が全角11文字：「半角英数字で」と「10文字以内で」
  - パスワードが空：「入力してください」と「8文字以上30文字以内で」
  - パスワードが半角の空白3つ、`あ`：「半角の英数字と記号で」と「8文字以上30文字以内で」

#### 2つの項目にエラーがあるとき（エラーの合計数）

| 入力 | A | B | C | D |
|---|---|---|---|---|
| ユーザー名 空、パスワード `あ` | 4 | 3 | **1**（ユーザー名の必須だけ） | 2 |
| ユーザー名 `あいう`、パスワード `abc12` | 2 | 2 | **1**（ユーザー名の形式だけ） | 2 |
| ユーザー名 11文字、パスワード 空 | 4 | 3 | **1**（パスワードの必須だけ） | 2 |

C は、前のグループにエラーがあると、**他の項目のエラーが表示されない**（直すまで見えない）。

#### 決定（B）

**エラーの扱い（設計書 6.9、G7 を見直した）：** 「必須」エラーが、他のエラーと重ならないようにする（形式の正規表現は空文字を通す）。それ以外のエラー（型変換・形式・文字数・範囲）は、重なったら**全部出す**。

理由：
- 1項目1つを守るには、D の自作の仕組みが要り、Phase 4〜6 の Form すべてに広がるため。
- 形式と文字数の両方が違うときは、どちらも直す必要があるので、両方見えたほうが1回で直せるため。
- C は他の項目のエラーが隠れるので使わない。

受け入れる点：
- パスワードが空のとき、「入力してください」と「8文字以上30文字以内で」の2つが出る。
- 重なったときの表示の順番が一定ではない。

- [x] 選んだ方法と理由を、設計書 6.9 と 6.10 の G7 に書いた。章8の D4 を消した

**確認**（`RegisterForm` を作った 4.6 のあとに、画面で確かめる。4.13 の(1)）：

|---|---|

| ユーザー名 `あいう` | ユーザー名は半角英数字で入力してください |
| ユーザー名 `abcdefghijk`（11文字） | ユーザー名は10文字以内で入力してください |

#### (8) 「途中で失敗したら全部取り消す」の確認（Q3-8。画面と SQL で行う）

登録の途中（ユーザー・科目・予算・取引先を保存したあと、支払方法を保存するところ）で失敗させ、**ユーザーも含めて何も残らない**ことを確かめる。アプリは起動したまま行う。

**失敗のさせ方：支払方法の表に、一時的な CHECK 制約を足す。** 支払方法は、登録の最後（6番目）に保存される。そこで、`payment_methods` の `user_id` が、これから登録するユーザーの `id` より小さい値までしか入らない制約を足す。すると、新しいユーザーを登録すると、支払方法の保存で DB が拒否し、それまでに保存したユーザー・科目・予算・取引先が、取り消されるかを確かめられる。

- 制約の値は、登録済みのユーザーの最大の `id`（今回は 36）にする（`SELECT MAX(id) FROM users;`）。新しく登録するユーザーの `id` は、それより大きくなるため、失敗する。
- 制約を足す・削除するのは `ALTER` なので、`hb_app`（`ALTER` の権限なし）ではなく、`root` で行う（開発用のデータベースだけに影響する）。
- 当初の案は、支払方法の表の名前を `RENAME TABLE` で一時的に変える方法だった。今回は、元に戻す操作が単純な CHECK 制約の追加・削除で行った。どちらの方法でもよい。

- [x] 自分で `root` のパスワードを入力して `mysql -u root -p` でログインし、一時的な CHECK 制約を足す（制約の名前は任意）

```sql
ALTER TABLE householdbudget.payment_methods ADD CONSTRAINT ck_tmp_user_limit CHECK (user_id <= 36);
```

- [x] ブラウザで、新しいユーザー名（`test4`）で登録を送信する。失敗して **5xx の専用画面**が出る（詳しい中身は出ない）


- [x] **必ず元に戻す**（`root` で）。制約を削除し、`SHOW CREATE TABLE payment_methods;` に制約が残っていないことを確かめる

```sql

```
