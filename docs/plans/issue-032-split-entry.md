### 2.4 DB の変え方と、Flyway を入れない理由

**今の仕組み**
- `schema.sql` の `CREATE TABLE IF NOT EXISTS` を、起動のたびに流す〔`spring.sql.init.mode=always`、`ddl-auto=none`〕。**すでにあるテーブルは変わらない**〔実行計画書の Phase 2 の共通事項〕。
- `hb_app` の権限は `SELECT, INSERT, UPDATE, DELETE, CREATE, INDEX, REFERENCES`。**`ALTER`・`DROP` はない**〔設計書 7.9〕。列を足すのは、本人が `root` で行う〔前例：Phase 7 の R15。`phase-7-comparison.md` の 4.4〕。
- 自動テストも開発用の DB につなぐ。表の形を変えると、すぐにテストと demo のデータの両方に響く。
- **MySQL の `ALTER` は、その場で確定する**〔暗黙のコミット〕。issue 019 の `START TRANSACTION`・`ROLLBACK` の型では取り消せない。先に `mysqldump` で控えを取る。

**Flyway を入れない理由**
1. 案 B の DB の変更は `ALTER` 1 回で、Phase 7 と同じやり方で足りる。
2. Flyway を入れると、`hb_app` に `ALTER`・`DROP` を与えるか、表を変えるための別のユーザーと環境変数を足すことになる。今の「権限は必要最小限」〔設計書 7.9〕を変えることになる。
3. すでにある DB に途中から入れるには、今の形を最初の版として登録する手順〔baseline〕と、`schema.sql` の仕組みをやめる変更が要る。テストと開発が同じ DB なので、手順を間違えると demo のデータに響く。
4. Spring Boot 4.1 と MySQL 9.7 で、Flyway の部品がそのまま動くかは、確かめていない。
5. それだけで issue 1 つの大きさがあり、032 と混ぜると、差分が読みにくくなる。
- 入れる意味が大きくなるのは、デプロイ〔Phase 10〕を行うとき。
